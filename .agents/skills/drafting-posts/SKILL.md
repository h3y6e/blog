# 記事の下書き

文脈を知らない読者でも最後まで追えるように、一本の記事としてまとめる。

書き始める前と推敲のときに[文章規範](references/prose.md)を読む。論証と表現の一般的な規範はそちらにまとめてあり、この文書が扱うのは素材の選び方、記事の組み立て方、このブログ固有の文体、出力の形である。一般の規範とこのブログの文体が食い違うときは後者を採る。

## 素材

渡された素材から書き、足りないときは足りないと伝える。変更の内容だけが分かって動機が分からない素材では記事の中心を決められないし、そこをもっともらしい理屈で埋めると、本人が考えてもいないことを本人の判断として公開することになる。

GitHub や Web は素材を補うために使う。非公開リポジトリも参照できるなら使ってよい。素材のメモは書き手の記憶であって仕様ではないので、技術的な記述は公式のドキュメントで裏を取る。

認証情報、限定公開の URL、個人名、アカウント識別子、社内のプロダクト名、社内文書の題名、ローカルのパスは、素材に混ざっていても本人が公開すると言わない限り落とす。

## 構成

節をどこで切るか、コードブロックをどれだけ説明してから出すかは文章にしにくいので、同じ種類の記事を `site/posts/` から一本開いて確かめる。手順の記事なら手順の記事、制作記なら制作記を見る。

書く価値を決めているのは引っかかったこと、意外だったこと、途中で分かったことのいずれかなので、そのうちの一つを記事の中心に据えて、そこから話を組み立てる。複数の話題を並べると、どれも中途半端になる。

説明の順ではなく考えた順に書く。前提があって問いが立ち、試して、まだ残っているという並びなら読者は書き手と同じ順に納得できるが、結果から逆算した説明は読みやすい代わりに、なぜそれを選んだのかが落ちる。

最初に何を誤解していたか、なぜその話題に戻ったか、何が未解決かといった書き手の立ち位置も残しておくと、完成した報告ではなく考えている途中の記録として読める。

見出しは環境、方針、経緯、工夫、結論のように、その節が何についてかを指す名詞句にする。節の結論を言い切る見出しにすると、読む前に結末が分かってしまう。

## 文体

文の長さ、段落の長さ、文字種の比率、文末の分布は textlint が検査するので、ここにはそれ以外を書く。

常体と敬体は記事ごとに統一する。既存の記事では、手順・解説・道具の紹介が常体、参加記・制作記・アドベントカレンダーが敬体になっている。

冒頭では扱う対象と目的を一、二文述べてから本題に入り、体験記の場合は出来事から始めてもよい。背景を積み上げてから本題に入る記事はこのブログには無い。

結びは一文で終え、本文で伝わったことをまとめ直す節は置かない。

段落と段落のつながりは書かずに、並べる順序で示す。長い論証なら接続詞で関係を明示するところを、このブログでは読者に委ねている。

読者に呼びかけずにやったことを書く。解説記事なら「〜してみてください」と書く場面でも「〜した」で止める。

留保や自信の無さは短い括弧に入れる。流れを止めずに、裏を取っていないと分かる形で書ける。

## 出力

`site/posts/YYYYMMDD-<slug>.md` に保存する。frontmatter は `title`、`date`、`tags`、`rss_description` で、tags は実際の題材から決める。公開できる参照は本文に置き、`{{ embed URL }}` は特に重要なものだけに使う。

## 仕上げ

`vp run textlint` を走らせて error を無くす。warning は残してよいが、一つずつなぜその形にしたかを言えること。言えないものは見落としなので直す。

そのうえで、事情を知らない読者のつもりで一度通して読み、頼まれた切り口が残っているか、公開できないものが漏れていないかを確かめる。

公開するのは本人が書き直してからにする。`site/posts/` の記事はすべて、次に `vp run calibrate-style` を回したときに閾値の母集団へ入るので、下書きのまま出すと textlint が次から基準にする文体の一部になる。
